# Проект: Диветро закупки бот

> **Это Диветро** (`divetro-zakupki-bot`) — изолированная копия логики бота
> Бертам (`zakupki-bot`). Код общий, но токен/база/деплой свои. Бертам не трогаем.
> Что настроить под Диветро — см. **`DIVETRO_SETUP.md`**. Разделы про сервер,
> домен и имена служб ниже пока унаследованы от Бертама — заменить на свои.

Сводка контекста, чтобы продолжить работу в новой сессии без повторного
объяснения истории. Бизнес-логика, архитектура и текущий статус.

> Важно: проект сильно эволюционировал. **Группы, реакций и окон приёма больше
> нет** — всё происходит внутри бота, подтверждение кнопками. Если встретишь в
> старых заметках «реакции в группе» или «окна 15:00–17:00» — это устаревшее.

## Бизнес-контекст

Компания металлоконструкций, 4 независимых сектора, каждый со своим
руководителем + менеджером, ведущими полный цикл (заявка → закупка → логистика):

- Покраска · Лазер/Гибка · Конструкции · Цех

Цель бота — единый простой процесс без шума: сотрудник подаёт потребность (что
нужно), закупщик оформляет заявку (поставщик, сумма, счёт), директор одобряет,
бухгалтер оплачивает, все видят статусы. Отделы работают **только через бота**.

## Как всё работает сейчас (актуально)

Всё в личных чатах с ботом. Никакой группы, никаких реакций.

1. **Потребность — упрощённая форма (Telegram Web App).** `/new` → кнопка
   «📋 Подать потребность» открывает веб-форму (`webapp/form.html`). Поля: сектор
   (авто), **что нужно** (текст), **нужно к дате**, **срочность** (обычная/скоро/
   срочно), необязательное фото/файл. Сотрудник **не знает** поставщика и сумму —
   это задача закупщика. Есть и запасной пошаговый мастер — `/new_text`.
1а. **Административные платежи (только директор).** В мастере `/new_text` у
   директора есть категория **«Административные»** (аренда, коммуналка и т.п.).
   Директор сам заполняет поставщика/сумму/счёт (полная форма), заявка авто-
   одобряется и идёт бухгалтеру, **без закупщика и логистики**.
2. **Закупщик — оформление потребности в заявку.** Закупщик получает карточку
   потребности с кнопками **📝 Оформить заявку / ✖ Отклонить**. Нажал «Оформить» →
   бот спрашивает поставщика, сумму, наряд, счёт (пошагово в чате). После
   оформления статус меняется на `оформлено`, заявка уходит директору на одобрение.
   Закупщик может отклонить потребность (сотруднику придёт уведомление).
3. **Белый список.** Подать потребность может закреплённый за сектором сотрудник
   (или директор/бухгалтер). Посторонний получает «обратитесь к директору».
4. **Реестр людей и ролей.** Таблица `people` (user_id → `sector` ИЛИ `role`).
   `/assign` назначает человека на сектор или роль: **Бухгалтер / Бухгалтер 2 /
   Закупщик / Водитель / Склад** (взаимоисключимо). Два бухгалтера — оба получают
   карточки оплаты, любой может нажать «Оплатить». Директор — через `.env` или
   роль (назначается админом). Один держатель на роль.
5. **Одобрение директора — кнопкой.** После оформления закупщиком директору
   приходит карточка (фото счёта + данные) с кнопками **🟢 Одобрить / ✖ Отклонить**.
   Заявку, поданную самим директором, система **авто-одобряет**.
6. **Оплата бухгалтера — в один тап.** Карточка с **✅ Оплатить** уходит обоим
   бухгалтерам. Нажал любой — «🟥 Оплачено», запускается логистика.
6б. **Платёжка — по запросу.** Кнопка **«📄 Запросить платёжку»** у водителя,
   сотрудника, директора. Механизм прежний (очередь + прикрепление).
6а. **Логистика — двумя кнопками.** Водитель → **🚚 Еду за товаром**,
   склад → **📦 Принял на складе**. Порядок строго последовательный.
7. **Единый прогресс-блок.** Все участники видят одинаковую историю:
   `🔵 Подано → 📝 Оформлено → 🟢 Одобрено → 🟥 Оплачено → 🚚 В пути →
   📦 На складе` (либо `✖ Отклонено`). `core.refresh_all_cards` обновляет
   карточки на месте. Статусы: `потребность → оформлено → одобрено → оплачено →
   в_пути → получено` (или `отклонено` на любом этапе).
8. **Просмотр заявок.** `/list` — по роли: сотрудник видит заявки своего
   сектора, директор/бухгалтер — все с фильтром по секторам. `/my` — только свои.
   `/report` — суммы/количества за месяц.
9. **Онбординг.** Ссылка-приглашение `https://t.me/Bertam_procurement_bot`
   (+ QR-код `invite_qr.png`). При первом `/start` нового человека директору
   падает пинг «ждёт закрепления». `/id` — показать свой Telegram-ID.

## Технический стек и структура

- Python 3.12 (на сервере), `python-telegram-bot` v22 (polling), `aiohttp`
  (веб-сервер формы), `python-dotenv`. SQLite — `zakupki.db`, единственный
  источник правды.
- `main.py` — команды и хендлеры. Два `ConversationHandler`: **employee_conv**
  (подача потребности: сектор → описание → дата → срочность → фото) и **buyer_conv**
  (оформление заявки: поставщик → сумма → наряд → счёт). Директор через `/new_text`
  может подать адм. заявку (полная форма, минуя закупщика). `action_callback` —
  кнопки `act:<action>:<req_id>` (approve/reject/buyreject/pay/ship/receive).
  `/assign`, `/list`, `/report`, онбординг.
- `core.py` — `publish_need()` (потребность → закупщику + монитор сотруднику),
  `process_need()` (закупщик оформил → директору), `publish_request()` (адм.
  заявка директора, минуя закупщика). `refresh_all_cards()` обновляет текстовые
  (buyer_msg, notify_msg) и фото-карточки (director, accountant, accountant2,
  driver, warehouse). `build_need_text()` — единый форматтер, адаптируется по
  наличию данных. `buyer_ids()`, `accountant_ids()` — резолвят роли из БД/`.env`.
- `webserver.py` — приём формы потребности: HMAC-проверка `initData`, белый
  список, публикация через `core.publish_need`. Эндпоинты `/form`, `/config`,
  `/mysector`, `/submit`, `/pay`, `/attach_payment`. Слушает `WEB_HOST:WEB_PORT`.
- `db.py` — SQLite. Таблица `requests`: колонки description, needed_by, urgency,
  buyer_msg_id, processed_by/at, accountant2_msg_id, need_photo_file_id/is_document
  (+ все прежние). Функции `create_need()`, `update_need_to_request()`,
  `set_buyer_msg()`, `set_accountant2_msg()`, `set_need_photo()`. Таблица `people`
  (`sector` ИЛИ `role` — Бухгалтер / Бухгалтер 2 / Закупщик / Водитель / Склад).
- `config.py` — `ROLES` (Бухгалтер, Бухгалтер 2, Закупщик, Водитель, Склад),
  `ADMIN_ROLES` (+ Директор). Env: `DIRECTOR_ID`, `ACCOUNTANT_ID`, `ACCOUNTANT2_ID`,
  `BUYER_ID`, `DRIVER_ID`, `WAREHOUSE_ID`. Устаревшее: `REACTION_*`, `WINDOW_*`,
  `GROUP_CHAT_ID`.
- `webapp/form.html` — упрощённая форма потребности (описание, дата, срочность,
  необязательное фото). Полная форма с поставщиком/суммой только через бот-мастер.
- `get_ids.py` — устаревший; ID узнавать командой `/id`.

## Развёртывание и разработка

- Боевой сервер: **Hetzner, `root@bertam.online`** (Ubuntu 24.04). Код в
  `/opt/zakupki-bot`, пользователь `zakupki`, служба systemd **`zakupki-bot`**.
  Веб-сервер отдаётся наружу через nginx: `location /zakupki/` → `127.0.0.1:8080`
  в `/etc/nginx/sites-available/bertam` (рядом с основным Node-проектом на 3001).
- На том же сервере есть **другой живой проект** (Node `gant-server`, PM2, 3001) —
  его не трогаем.
- С Мака доступ к серверу по SSH-ключу (root). Деплой одной командой:
  **`./deploy.sh`** (tar → scp → py_compile → pip → restart). Логи: **`./logs.sh`**.
  Памятка разработчика — `DEV.md`. Полное развёртывание с нуля — `DEPLOY.md`.
- `.env` (токен, `DIRECTOR_ID`, `ACCOUNTANT_ID`, `ACCOUNTANT2_ID`, `BUYER_ID`,
  `WEBAPP_URL`) и `zakupki.db` — только на сервере, в git и архив деплоя не попадают.
- ВАЖНО: один токен = один процесс. Не запускать `python main.py` локально,
  пока бот работает на сервере (конфликт `getUpdates`).
